Operation page: review and layout samples

Checked at 1440×900 with 10 alerts and 7 decisions waiting. Each sample below uses made-up data and works on its own; nothing in them calls the app.

What the review found

Decisions start below the fold

The crew roster takes the top of the left column (about 240 px), so at 1440×900 Alerts start halfway down the screen and about one and a half cards show.

The first Approve is the fourth card

Two Executive briefs and a road-closure notice with only "Got it" come before the first card that needs a decision. Each card is about 286 px tall.

Everything shouts Critical

An Executive brief is tagged Critical with a red border and glow, the same as a burst main. When every card is red, the real emergencies don't stand out.

The key numbers do nothing when pressed

"Waiting for your decision 7" is the most useful number on the page, but it is not a button. It could filter the list to those 7.

Demo tools sit beside operator tools

Scan now, Compare imagery and Simulate an event share the header with the AI Agents switch at the same weight. In a live room they belong in one menu.

The map corners are crowded

Search, Urban change, the Mobility layers list, 2D/3D and the legend all float over the map. The feed cards for the 7 data sources sit below the fold.

Keep: the approval safety

Two presses to approve, "If approved" text, the lifecycle strip and "How the crew handled this" are clear and should stay in every layout.

Keep: one brand, two languages

The green, IBM Plex Sans Arabic, right-to-left and dark mode already work. The samples use the same green and font.

Set 4: shadcn/ui style, light and dark

A cleaner, neutral style in the shadcn/ui manner (Tailwind CSS), keeping the Falcon Eye green, the font and the real map. Each page has a dark mode (the moon button). Approve opens a confirm dialog instead of the two-press button. It keeps the same safety and also shows what will happen. The failure, retry and states from set 3 are here too.

Set 3: same look, new ways to decide

Also built on the Operation page's own styles and the real map. Here Approve behaves the way a real request would: it shows "Approving…", then the result, and moves you to the next decision. APR-0008 fails once on purpose, so you can see a failure that leaves the other alerts alone.

States every set-3 page handles
  • Loading: grey placeholders, announced as busy.
  • No alerts: says so, with Scan now.
  • Server offline: says what failed, shows no stale data, offers Try again. The map says it needs internet.
  • Approving: the card's buttons are disabled until the answer comes back, so nothing is sent twice.
  • Done: "✓ Approved and done · WO-… created" on the card, read out to screen readers; focus moves to the next decision.
  • One failure: the reason in plain words and Try again, on that card only.
  • Viewer: no Approve or Reject anywhere, and a line that says why.
  • Long names: long road and person names wrap or shorten; nothing runs off the screen.

Set 2: same look, different layout

These use the Operation page's own styles, cards, crew colours and the real ArcGIS map, so only the arrangement differs. Each has a "Preview a state" menu: loading, no alerts, server offline, and signed in as a viewer (no Approve).

Design contract for set 2
  • The page's job: let the operator see what needs a decision and decide it, without scrolling at 1440×900.
  • Main action: Approve, two presses, on the alert card. Never offered to a viewer.
  • States: loading, no alerts, server offline, viewer, normal.
  • Order: decisions first, then reports to check, then information. Briefs are Info, not Critical.
  • Rejected: a new colour scheme, a drawn map, removing the crew from view.
